## 2. Complete Data Collection Methods (every mechanism in use)

### 2.1 Plain-HTTP scraping of product pages — VM watchlist (`scrape.py`)
- **How:** 15 ASINs from `targets.txt`; for each, `common.fetch_html` tries routes cheapest-first: ① direct requests+HTML from the VM, ② SOCKS tunnel via phone, ③ relay (Render API fetches through its IP), ④ headless Firefox through the tunnel (only if tunnel up).
- **Why:** deepest data per product (title, price, MRP, discount, rating, reviews, BSR rank+category, seller, availability, image) — Amazon's product pages are server-rendered.
- **Advantages:** free, precise selectors, full field coverage, cheapest route first.
- **Limitations:** datacenter IP gets blocked; browser route needs the tunnel; 12–25s pause between products.
- **Speed:** full 15-product pass ≈ 5–10 min (318s measured on a clean run).
- **Reliability:** 55.6% slot yield while blocked; ~100% when IP is clean.
- **Cost:** ₹0. **Scalability:** poor beyond ~30 products/day on one IP.
- **Use case:** competitor price history for the 15-ASIN watchlist.

### 2.2 Plain-HTTP scraping of list pages — nightly collector (`scraper/collector.py`, GitHub Actions)
- **How:** fetches Best Sellers / New Releases / Most Wished For / Most Gifted for **31 Amazon.in categories** (124 list pages/night), parses product cards by stable substrings (`zg-bdg-text`, `data-asin`, aria-labels, rupee regex) — never hashed CSS classes.
- **Why:** broad market discovery — ranks, entrants, movers across the whole catalogue.
- **Advantages:** runs on GitHub's IP (rotates per-run), zero infrastructure, partial-failure isolation (one category failing never aborts the run).
- **Limitations:** Movers & Shakers returns no server-rendered products (verified — excluded deliberately); ~19% of rows have no price (no live offer that day); one snapshot per page per night.
- **Speed:** ~124 pages in ~45 min (≈3 pages/min).
- **Reliability:** success run after success (latest: Aug 29 22:47 UTC ✅).
- **Cost:** ₹0 (GitHub Actions free minutes — budget was 77% consumed before the monitor was throttled to 4×/day).
- **Use case:** the 117,901-row trend-radar dataset (Jul 6 → today).

### 2.3 Browser-automation visual scraping — Maxun robots (laptop)
- **How:** Maxun robots (headless Chrome) mirror Amazon bestseller pages locally; results POST to `/ingest/maxun`.
- **Why:** residential laptop IP doesn't hit datacenter-IP blocks; visual robots survive layout changes better.
- **Advantages:** consumer IP; can capture JS-rendered content.
- **Limitations:** laptop must be on (~1 h/day by design); robot coverage is still partial (Grocery robot is the main one; `add_category_robot.py` clones more).
- **Speed:** ~30 products/robot/run; **rows: 26,310** (latest write 1 h ago).
- **Cost:** ₹0. **Reliability:** good when the laptop runs; silently stale when it doesn't (advisory-only in the monitor).
- **Use case:** hourly daytime category capture.

### 2.4 Amazon SP-API sync — storefront (`/storefront/sync-all`, GitHub 21:15 UTC daily)
- **How:** GitHub pings the API; Render holds LWA credentials + encryption key and pulls the connected seller's sales/orders.
- **Why:** first-party data no scraper can get.
- **Reliability:** success on every recent run. **Cost:** ₹0.

### 2.5 HTML parsing (no JS rendering) — both scrapers
- Collector and VM scraper parse server-rendered HTML with BeautifulSoup/regex. No headless browser is used on the cloud paths (deliberate: cost + IP reputation). The only browser path is Maxun and the VM's emergency Firefox-through-tunnel route.

### NOT in use (asked about explicitly)
RSS/XML feeds, sitemaps, search-engine crawling, OCR, PDF parsing, third-party datasets, manual imports — **none are part of the pipeline today**. AI extraction exists only as user-facing enrichment (see §4/§11), not collection.

## 4. Data Quality Analysis

**Accuracy — strong by construction:**
- Price selectors are scoped to `#centerCol` (the real buy box). A page-wide fallback was removed after it confidently scraped a *carousel* product's price (documented first-run bug).
- BSR parsed only from the product-details block (the "#N in Category" string appears in widgets for *other* products otherwise).
- Monitor verifies deployed build fingerprint vs. the last commit that touched `api/`.

**Validation gates at ingest (measured in code, `/ingest/maxun`):**
- ASIN regex; rating clamped to 0.5–5.0; price 1–10,000,000; reviews/rank 0–10M — out-of-bounds values become NULL, never junk.
- `collected_at` must parse and fall between a plausible floor and now+1 day — backfills keep their real scrape timestamps.
- Titles HTML-unescaped on write **and** on read (legacy rows fixed too).
- VM push sends **only ok=1 rows** — a failed fetch never writes a hole.

**Completeness:** ~81% of collector rows carry a price (64,083/79,099 measured 31 Jul); title/rating/reviews near-complete. Missing price = genuinely no offer that day (information, not error).

**Consistency:** category labels are frozen by convention ("never rename an existing key" in code) because renaming fragments history. `Competitor Watchlist` is deliberately kept outside the 31 radar categories so watchlist rows don't pollute bestseller trend math (weekly_digest filters by category).

**Duplicates / error rate:** see §5. **Confidence score:** not implemented per-row (recommendation below).

**Weaknesses:** (1) no per-row provenance/quality flag in Supabase; (2) `maintenance-failed` heartbeat label is a cosmetic mislabel (backup actually succeeded); (3) collector has no post-parse sanity check that a page returned ≥N products.

## 5. Data Originality

| Question | Answer |
|---|---|
| Original data? | **Yes — 100% first-party scraped from amazon.in**, the primary source. No third-party dataset resells anything here. |
| Copied from a provider? | No. |
| Aggregated? | Yes, but from primary pages only. |
| AI-enriched? | Only user-requested features (`/listing/suggest`, `/listing/review-summary` via OpenAI, degrade to 503 without a key). **Enrichment never writes back into snapshots** — the dataset stays raw/factual. |
| Transformed before storage? | Field mapping (price_history→snapshots schema), timestamp normalisation to ISO/timestamptz, HTML unescape. Titles/prices stored verbatim. |
| Duplicates removed? | Dedupe is **source-side, not DB-side**: VM push keeps a `.pushed_id` watermark (idempotent, resume-safe); collector writes each page once nightly. |
| Normalised? | Yes — one `snapshots` schema for all three writers. |

**Honest risk found in audit:** `snapshots` has **no unique constraint and `insert_snapshot_rows` is a plain INSERT**. The watermark prevents normal duplicates, but `push --all` (a supported flag) or a botched replay would double rows. **Recommendation R2 below closes this.**
**Conflicting information:** not merged — each snapshot is a point-in-time observation; history *is* the product. Conflicts don't arise by design (append-only).

## 8. Data Storage

- **Supabase Postgres** (production): `snapshots` table — `asin, category, list_type, rank, title, price, rating, review_count, image_url, collected_at (timestamptz, migrated)`; 3 migration SQL files in repo. Reads go through indexes on asin+collected_at (ORDER BY collected_at in hot paths).
- **VM SQLite** (`scout.db`): staging + local history — `price_history` with per-run rows, route/flags/notes columns, index on `(asin, scraped_at)`; auto-migration for late columns.
- **VM files:** `runs.jsonl` (ops history), `data/.offset` (rotation), `.pushed_id` (watermark), nightly gzip backups (`~/backups`, pruned, integrity-checked — latest `scout-20260830.db.gz`, integrity ok).
- **Retention:** ops events pruned nightly (retention policy in `ops.py`); backups pruned (1 pruned on 28 Aug); snapshots retained indefinitely (the asset).
- **Partitioning/versioning:** none (not needed at 145k rows; revisit at millions).
- **Standing security rule:** the scraping VM never holds the production `DATABASE_URL` — it only ever talks to the API.

## 9. End-to-End Pipeline

1. **Discovery** — `discover.py` (search-term → ASIN candidates) + DB-driven selection (top rank-holders by days-seen/reviews, read from snapshots on 12 Aug).
2. **Scheduling** — systemd timers on VM; GitHub cron in cloud; both windowed to free-tier budgets.
3. **Fetching** — route ladder: direct → tunnel → relay → browser-via-tunnel; block detection by page size; early abort after 4 consecutive blocks (protects the IP).
4. **Parsing** — scoped CSS selectors + regex; carousel-safe price logic; stable-substring list parsing (hashed-class-proof).
5. **Cleaning** — whitespace collapse, HTML unescape, money parsing to float, availability markers.
6. **Validation** — bounds clamps at ingest; timestamp plausibility; ok=1 gate; failure rows kept locally with notes but never pushed.
7. **AI enrichment** — none in the data path (user-facing only).
8. **Duplicate prevention** — watermark (`pushed_id`); append-only snapshots.
9. **Transformation** — column mapping price_history→snapshots; category pinning (`Competitor Watchlist`).
10. **Categorisation** — 31 frozen labels; watchlist pinned outside them.
11. **Storage** — Supabase `snapshots` via `/ingest/maxun`.
12. **Indexing** — asin+collected_at ordering; timestamptz migration.
13. **API availability** — 47 endpoints (trend-radar, watchlist, product-database, drawer-details, storefront, profit-calculator…).
14. **Consumption** — Next.js web on Vercel (scoutveda.com, HTTP 200, 1.9 s) + monitor checks.

## 10. ScoutVeda Integration (how the product consumes the data)

- **Receive:** `POST /ingest/maxun` with `X-Scout-Key` — the single write door (VM push + Maxun bridge both use it).
- **Direct DB access?** Only Render holds `DATABASE_URL`. The VM and GitHub never do.
- **Synchronization:** hourly push ticks (0 backlog); nightly collector; daily storefront sync; laptop robots hourly-when-on.
- **Update propagation:** immediate — push commits → next API read sees it.
- **Stale data:** never overwritten; staleness is *measured* (`data_age_hours` in the 15-min watchdog, `collection_dates` in digest, 48 h collector alarm in monitor).
- **Modules depending on it:** trend-radar (digest/categories/per-category), watchlist, product-database, drawer-details, competitor-analysis, listing-health, alerts, storefront analytics.

## 12. Data Lifecycle — one record traced (Tata Salt, B07575FPC3)

1. Chosen 12 Aug from DB evidence (84,087 reviews, avg rank 2.0, 31 days seen) → `targets.txt`.
2. 12:10 IST timer fires `scrape.py` → direct fetch (~2 MB HTML) → blocked? → relay attempt.
3. Parsed: price ₹29, rating, reviews, BSR → `validate.py` checks → row written to SQLite (ok=1, route recorded).
4. :35 push tick → only ok=1 rows after watermark → POST `/ingest/maxun`.
5. API clamps/validates → INSERT into Supabase `snapshots` (category="Competitor Watchlist", real scrape timestamp preserved).
6. Served live via `/watchlist`, `/product-database`, drawer-details; monitor asserts yield ≥7.5/15.
7. Updates = new snapshot rows; nothing overwritten; VM SQLite pruned via nightly backup rotation; ops events pruned nightly.

## 14. Scalability

| Scenario | Verdict | First wall |
|---|---|---|
| 10× data (1.45M rows) | Fine | Postgres fine; need real indexes/partitioning later |
| 10× watchlist (150 ASINs) | **Blocked** | single-IP block economics — needs residential/rotating IPs |
| 100× users | **Blocked** | Render free tier (750 h/mo, shared CPU); Postgres connection count |
| 100× websites | Architecture unchanged | one scraper per site family; scheduler moves to a queue |
| More categories | Easy | collector scales linearly; GitHub minutes are the budget |
| Global expansion | New problem | per-domain parsers, per-region bot-wall economics |

**Free-tier ceilings already budgeted:** Render hours (windowed pinger), GitHub minutes (monitor throttled 16→4/day after the 480-min/mo arithmetic error was found and documented).
